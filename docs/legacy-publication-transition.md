# Authorized legacy publication transition

This is a bounded, offline data-change procedure for the October 30, 2026 request to publish entries previously submitted for review and fill missing public usernames from verified owners' email prefixes. It is separate from the code-only release. The planner has no network or apply command; deployment and production mutation are not side effects of building, testing, or visiting a page.

Deploy and verify the image and public-attribution code through the approved release route first. If deployment access is missing, retain the plan privately and stop before applying it. Reconcile the serving source revision, obtain a fresh recovery bookmark, and repeat the read-only snapshot immediately before applying a plan. The source snapshot hash must match; changed content requires a fresh plan, not an overridden guard.

The single `LEGACY_SNAPSHOT_SQL` read in `scripts/lib/legacy-transition.mjs` selects at most 20 older candidate submissions, their necessary revisions/history/media metadata, affected target records, and verified owner prefixes. It never selects full emails, account names, unrelated accounts, or image bytes. Store the snapshot under `.local/` with directory mode 0700 and file mode 0600. Keep it out of Git, screenshots, public logs, and reports.

Run `node scripts/plan-legacy-transition.mjs PRIVATE_SNAPSHOT NEW_PRIVATE_DIRECTORY`. The output directory must be new and under `.local/`. The generated plan includes the snapshot hash, before/after copies, guarded forward statements, guarded rollback statements, and an aggregate report. Inspect skipped reasons and selected image rights privately. A library or creator name is not a license: ambiguous and unknown rights retain the image privately. Original submissions and uploaded bytes are preserved. New notes may refresh a public target reference; this does not reapply historical field edits.

Only verified ownership plus an owner-authored submission event establishes eligibility. Draft, withheld, changes-requested, rejected, revoked, deleted, unresolved jobs, hidden attribution, and unsupported contribution types stay unchanged. Chosen usernames win. Equal prefixes remain distinct verified-owner attribution identities. Already published legacy releases receive a revision-bound public-attribution audit event rather than changes to their immutable content or approval. Public GETs never query account emails.

Apply the generated forward statements in one atomic D1 batch under the separately authorized data-change procedure. A repeated batch is a no-op. Each publication uses the existing publication service's validation and projection, with a policy audit marking operator initiation and verified-owner attribution; it does not manufacture a review or pretend an owner clicked Publish. The SQL guards the head, original revision hash, verified prefix, target state, jobs, and rollback receipt. No schema migration or credential change is needed.

After applying, reconcile each expected receipt and head, the public projection, image access and contributor totals against the plan. Report counts and statuses only. A zero-change receipt guard means stop and re-read; do not force an outdated plan. Retain the protected backup, plan hash, bookmark, code revision, and execution/readback receipt.

Rollback is an atomic batch too. It requires exact after-state matches and unchanged event counts, restores only affected rows from the protected before copies, and removes only rows inserted by this transition. Original participant history and media are retained. A later writer blocks rollback; never bypass that guard or restore the entire database over unrelated work. The rollback audit receipt remains, repeat rollback is harmless, and the same forward plan cannot reapply after rollback. This is recovery for the exact transition, not a general-purpose history deletion tool.
