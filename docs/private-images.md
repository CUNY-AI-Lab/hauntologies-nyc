# Private proposal images

This implementation is staged locally. The live Worker has no enabled contribution identity configuration, and migration `0005_contribution_media.sql` has not been applied remotely.

The existing D1 database can hold the bounded prototype without a new bucket or credential. Each retained image is at most 1,048,576 bytes, each proposal can receive three images, and all retained images together are capped at 33,554,432 bytes. The multipart request limit is 1,064,960 bytes, including an 8,192-byte metadata allowance. An individual D1 value/row may not exceed 2,000,000 bytes; image bytes live in a separate row rather than being repeated in revision JSON. See [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) and [binary parameters](https://developers.cloudflare.com/d1/worker-api/).

The browser checks file signatures and dimensions before decoding, then draws and reencodes a derivative. The original file on the contributor's device is untouched. The server independently checks JPEG, PNG or WebP container structure, type and dimensions and strips embedded metadata. Maximum dimensions are 8,192 pixels per side and 16,777,216 pixels total. SVG and animated images are rejected. Server checks are not a full image-codec decode or malware scan. Files are served only as private downloads, with `no-store`, `nosniff`, a sandbox policy and a server-generated filename. Caption, credit, source URL, rights and alternative text are retained separately as contributor-authored metadata; unknown rights do not become publication permission.

`POST /api/contributions/attachment` accepts a saved proposal ID, expected revision, idempotency key, metadata JSON and image. Only that proposal's contributor can upload. The transaction stores the derivative, creates a new immutable proposal revision, invalidates the previous approval, and records an audit event and receipt. Readback verifies the retained byte count and SHA-256 before success. Retries reuse the request key and exact file/metadata; a changed request conflicts. Concurrent writes must pass revision and quota checks in the same transaction. Images never alter public records automatically.

`GET /api/contributions/attachment?id=…` checks access to the linked private proposal before retrieving image bytes. The regular contribution gate must verify the server identity first; client identity headers do not grant access. Private downloads have no public asset URL. The migration adds a table and index and prevents attachment updates; it does not modify or delete original records.

The form stages sanitized files in memory. A file remains **Not uploaded** until a verified server receipt. Text is saved first; an image failure leaves that contribution saved and offers an image retry against the same proposal. Files are not written to browser databases. Closing the tab with unsaved files triggers the browser's standard warning; a browser crash can still lose those unsaved files.

Activation requires review of this migration against the existing schema, the separately approved CUNY identity connection and verified owner subject, and an explicitly authorized synthetic production save/readback test. No migration, role grant, identity binding or production test write is performed by the build. Initial owner access does not grant another person reviewer or publisher permissions.
