# Map accounts

CUNY Login was withdrawn on October 22, 2026. The proposed IDENTITY connection to cail-doorway/WorkerIdentity is cancelled. Do not create it or configure CUNY audiences, public keys or owner subjects. The earlier Gmail/Cloudflare Access proposal was also not approved. Neither is a substitute for map-specific accounts.

The local withdrawal candidate removes CUNY signup/password-recovery links, removes the CUNY adapter from the Worker import/build path, and blocks obsolete CUNY-enabled settings without falling back to Access. Historical adapter source and standalone tests remain recoverable and are not bundled. The public map and `/register` remain independent. No account service has been activated or represented as working by this change.

## Proposed implementation

Use a maintained email/password library inside the existing Hauntologies Worker, backed by the existing D1 database. Better Auth is the candidate for local compatibility evaluation: its official documentation covers email/password verification/reset and lists Cloudflare D1 through a Kysely community dialect. It is not installed, pinned, runtime-tested or security-approved in this branch yet. Do not write a new password cryptography implementation or assume SQLite support alone proves Worker compatibility.

Keep the interface small: Sign in uses Email and Password, with Reset password and the requested "Don't have an account? Register here." link. Account registration is separate from event RSVP. Verification must prove mailbox control before enabling the account. Verification must not make a password previously chosen by an attacker usable: set the initial password after mailbox proof, or bind proof to the initiating browser and require password confirmation. No unverified session may submit or read contributions.

The proposed account route prefix is `/api/auth/`, with exact allowlisted signup, verification, sign-in, session, sign-out and reset actions. Confirmation pages remain on `https://hauntologies-nyc.ailab-452.workers.dev`. The final library paths and generated schema will be reviewed after the local compatibility test. Disable social providers, account linking, generic admin plugins and unused endpoints. No CUNY identity or password is collected.

Use additive, namespaced tables for users, password credentials, sessions, verification/reset challenges and durable rate counters. They are separate from `event_registrations`, contribution revisions, review logs and existing identities. Store only a vetted password hash and its parameters; never plaintext passwords. Keep one Hauntologies-only application secret in Worker secret storage, outside source, logs and browser assets. No production secret is generated by this candidate.

Sessions use Secure, HttpOnly, SameSite host-only cookies with a one-hour limit initially. Enforce the exact map origin and CSRF defenses. Session/user IDs are server-generated and immutable. New account actors use a distinct map-specific namespace; they must never imitate old Access/CUNY actor IDs. The gate removes client identity headers before deriving an actor from a verified session. Private responses remain no-store.

Verification/reset tokens are purpose-bound, expiring and consumed once; safe storage and concurrent consumption must be tested. Reset changes the credential and revokes existing sessions. Generic responses and durable IP/account rate controls limit enumeration and mail abuse. Passwords and tokens never enter analytics, URLs outside the fixed confirmation flow, browser storage, screenshots or ordinary logs. Local Worker runtime tests must establish KDF cost and request limits before activation.

## Mail reuse

Read-only inspection found an existing Amazon SES v2 sender inside `cail-tools-admission`, From/Reply-To `ailab@gc.cuny.edu`, region `us-east-1`. Its bug-report entrypoint permits different callers and a fixed recipient; it is not authorized for Hauntologies accounts. Admission's existing account-link helper expects an already verified identity and is not an email/password provider. Live sender eligibility and mailbox delivery have not been checked in this change.

Proposed connection, not applied:

```json
{
  "binding": "ACCOUNT_MAIL",
  "service": "cail-tools-admission",
  "entrypoint": "AdmissionHauntologiesAccountMail"
}
```

The new entrypoint would permit only the Hauntologies caller and `verify_email`/`reset_password` templates. It constructs exact same-origin callback links and fixed subjects/sender; it does not accept arbitrary email bodies, senders or redirects. Recipient and challenge fields are bounded, rate limited and tied to an account action. Existing SES credentials remain inside Admission; they are not copied or read. Durable delivery state stores no passwords or plaintext tokens. Provider acceptance is separate from inbox delivery. Ambiguous sends remain unknown and are not blindly retried.

This account-mail capability does not include registration alerts, bulk messages or messages to an owner notification address. Their previous proposal remains unapproved. Existing SES usage may be metered; verify current eligibility and limits before sending. No free-delivery guarantee, new paid plan or spending increase is implied.

## Ownership and existing records

Verified new accounts may submit and read only their own proposals after activation. They receive no reviewer, publisher or attendee-list access by default. Each request verifies ownership server-side; local registration receipts and typed emails never authorize private reads.

The owner must select the email address for the map account, verify it, and confirm the resulting immutable account ID. The prior CUNY username and notification email are not an owner credential. Configure that ID explicitly; never make the first registrant an administrator. The minimum proposed owner grant is read-only access to this event's attendee dashboard. Review/triage/publishing grants remain separate and empty unless explicitly selected. Self-approval stays prohibited.

Do not query or join event RSVP rows by a typed or newly verified email to acquire historical contributions. No automatic migration or account linking occurs. The three previously recorded RSVP rows and all original evidence remain untouched. Even a verified email alone does not establish ownership of old submission identities. Any later linking needs its own reviewed proof and explicit action.

## Exact activation decisions

Before activation, complete the library/runtime candidate and inspect its generated additive migration. Then obtain action-time approval for:

1. Applying only the reviewed auth/rate/delivery tables to existing D1 `hauntologies-nyc` (`df7f1e92-e339-4e25-ac30-989dd68d8dfc`), preserving existing rows and taking an approved backup first. Do not include the unrelated private-image migration automatically.
2. Creating one Hauntologies-only auth secret and enabling account routes on the existing `hauntologies-nyc` Worker. Proposed signup scope is any email address that passes verification, with own-proposal access only and one-hour sessions. No other app permissions change.
3. Adding the exact ACCOUNT_MAIL binding and restricted Admission entrypoint above, using the existing sender and eligible SES service for verification/reset messages only. This is a new persistent service capability and is not yet approved.
4. Selecting the owner's account email and, after verification, granting the confirmed immutable account ID read-only attendee-dashboard access. No guessed owner or reviewer identities.
5. One explicitly labeled production verification/reset round trip and synthetic proposal save/readback/withdrawal using an approved test mailbox. State retained audit rows and email side effects first. Do not add event RSVP test rows without separate approval.

These are pending decisions, not executed operations. No rejection is being bypassed. No production account, email, schema or permission change was made.

## Local acceptance before release

Use synthetic local users and a fake mail transport. Cover pending signup, wrong-password/unknown-user responses, preregistration takeover prevention, token expiry/replay/races, origin/CSRF rejection, durable rate enforcement, session expiration/revocation, reset revocation, spoofed identity/role denial, IDOR between two users, owner-only attendee reads, unchanged RSVP data, no automatic old-account linking, transient database/mail failures and uncertain receipts. Exercise the actual compiled Worker/D1 adapter, not only Node mocks. Review password hashing parameters and pinned dependency advisories. Keep all pending settings absent from deploy config until approved.

Current withdrawal tests exercise obsolete-config rejection, encoded routes, forged identity headers, unchanged synthetic RSVP rows/idempotence and removal of CUNY links/imports. They do not prove working map sign-in, verification, reset or production email delivery.
