# Code-only production release

This procedure is for a reviewed code release that needs no database migration. It can be used only after the corresponding workflow is approved and merged to `main`, the required release approvals are in place, and the CI deployment credential is configured. A release that changes migrations or needs database access must stop and use a separately authorized database procedure. It does not establish that the live database schema or migration ledger is correct.

1. Review the exact proposed source and the changes since the source tag on the serving Worker. Check that the runtime and startup code, package scripts, build, preparation and deploy steps do not run migrations or other schema-changing SQL. The CI gate rejects differences under `drizzle/` or any `migrations/` directory, a deploy-time build command, and migration settings in the prepared Worker configuration. Source review is still needed: the file-diff check cannot prove arbitrary application code never changes a schema.
2. After review and the required repository approvals, dispatch `Release Hauntologies` on `main` with the full current main commit SHA. CI checks that the requested revision, workflow revision, checkout and current `main` agree. It installs the lockfile dependencies, builds and prepares that revision, and runs the synthetic test suite before the deployment credential is exposed to the release step. It checks `main` again before deployment and reports a change found after deployment.
3. CI verifies the exact prepared Worker identity, settings, asset routes, variables, database binding and mail-service binding. It reads the current Worker version and binding metadata, requires a resolvable source tag, and fails closed if the migration files differ. It preserves existing variables with `--keep-vars`. Changes to bindings or variables need separate review. The intended CI secret is `CLOUDFLARE_API_TOKEN`; the token must have the approved scope for this Worker. The exact endpoint permissions required by the pinned Wrangler version still need to be verified with that token.
4. CI deploys the prepared Worker and checks that the sole serving version has the requested source tag. It compares the binding metadata and hashes of plaintext variables to the pre-deployment snapshot, checks `/api/access-status`, confirms the signed-out contributor roster returns 401, and compares the delivered map HTML, scripts and styles for these workflows with the prepared files. The access-status response checks configured account readiness; it does not check the database schema or confirm that sign-in works. Provider metadata exposes secret names, not values, and does not return the mail-service props; those props are checked in the prepared configuration only.
5. Record the workflow result and serving revision. CI records the prior Worker version and UTC time, but does not query D1, count rows, inspect schema or ledger entries, or obtain a Time Travel bookmark. A timestamp is not a verified bookmark. If deployment or readback fails after submission, inspect the serving version and bindings before deciding whether a retry is safe. Mailbox verification and reset round trips require a separately authorized human using a mailbox they control.

The database procedure in [Running the site](running-the-site.md#release) remains separate. Review and authorization are required before obtaining a D1 bookmark, inspecting its schema or migration ledger, running any migration, or changing the database. Do not treat this code-only procedure as permission to read participant data or to change database state.
